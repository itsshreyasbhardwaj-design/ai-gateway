# Contributing

## Getting set up

```bash
pnpm install
pnpm dev          # gateway on :8787, no database or Redis needed
pnpm test         # unit tests, ~1s
pnpm test:e2e     # end-to-end against a real in-process gateway
```

Requires Node 20.10+ and pnpm 9+. Nothing else.

## Before opening a pull request

```bash
pnpm lint
pnpm typecheck
pnpm test
pnpm test:e2e
pnpm build
```

CI runs all of it.

## How this codebase is organised

Read [docs/architecture.md](./docs/architecture.md) first. The short version:

- **Adapters own all vendor translation.** No route handler branches on provider
  id and no vendor wire shape reaches the router. If you find yourself adding an
  `if (provider === …)` outside `packages/providers`, the abstraction is wrong
  somewhere.
- **Storage is behind a contract** with in-memory and Postgres implementations.
  The in-memory one is not a stub — it enforces the same tenant scoping, so a
  cross-tenant bug fails in tests rather than only in production.
- **Time is injected.** Retry backoff, circuit breakers, budget periods and
  rate-limit windows all take a `Clock`. Tests advance it instead of sleeping.

## Adding a provider

Most vendors speak the OpenAI wire format and need only configuration —
`POST /api/v1/providers` with a base URL and model list, no code.

For a genuinely different API, see the worked example in
[docs/providers.md](./docs/providers.md#writing-an-adapter). Three rules:

1. Report the **gateway** model id, never the upstream one.
2. Honour `ctx.signal` — it fires on client disconnect and deadline.
3. Never echo upstream error text into a user-facing message; it can contain
   the caller's own prompt.

Adapters need tests covering request translation, response translation,
streaming, cancellation and error classification. `packages/providers/src/testing.ts`
has a stub fetch that emits SSE in small pieces, so chunk-boundary handling is
actually exercised.

## Testing expectations

**Test behaviour, not implementation.** `packages/router/src/execute.test.ts` is
a reasonable model: it asserts that a malformed request is not replayed across
providers, not that a particular function was called.

**Security changes need adversarial tests.** Assert the attack _fails_. See
`tests/e2e/security.test.ts`.

**Anything time-dependent uses `FakeClock`.** A test that sleeps is a test that
will be flaky on a loaded CI machine.

## Things the project will push back on

- **Any claim about model quality.** The gateway measures cost, latency and its
  own observed success rate. It does not rank output quality, and a composite
  "score" would imply a judgement it cannot defend.
- **Hardcoded pricing.** Prices are configuration, versioned, and labelled with
  their source.
- **Silent behaviour.** If the gateway adjusts, substitutes or refuses
  something, it is recorded on the trace and surfaced. A quietly clamped
  `max_tokens` is worse than a rejected request.
- **Fabricated data.** Demo data is generated by sending real requests flagged
  as test traffic, never by writing rows into the analytics tables.
- **Failing open on spend.** A counter outage must not let a budget be exceeded.

## Commits

Conventional commits (`feat:`, `fix:`, `perf:`, `docs:`, `test:`, `security:`,
`refactor:`). Explain _why_ in the body, not just what — the diff already says
what.

## Reporting bugs

Include the gateway version (`GET /`), what you expected, what happened, and a
request id if you have one — it resolves to a full trace.

Security issues go through [SECURITY.md](./SECURITY.md), not the issue tracker.
